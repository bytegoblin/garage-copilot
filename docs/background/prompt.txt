# DIY Assistant — Step 1: Repository Analysis and Architecture

You are the lead architect for a new Claude Code project called **DIY Assistant**.

We are going to build this project incrementally, step by step.

**Do not implement the complete application yet.**

Your task in this step is to inspect the current repository, understand the available Claude Code capabilities, and design the foundation of the system.

Do not create the full set of agents, hooks, skills, MCP integrations, workflows, or final outputs yet.

## Product Vision

DIY Assistant will eventually be a reliable agentic workflow for helping a user research, plan, and execute DIY projects.

The initial domain is a personal home workshop, but the architecture should later support:

- home improvement;
- furniture building;
- smart-home projects;
- automotive DIY;
- repairs;
- tool and equipment selection;
- material selection;
- other practical DIY projects.

The user will interact with the system in natural language through a Claude Code slash command such as:

```text
/diy Помоги спланировать обустройство моего гаража под столярную мастерскую.
```

The user communicates primarily in Russian.

## Language

The coordinator and all user-facing communication must be in Russian unless the user explicitly requests another language.

Human-readable artifacts should normally be written in Russian.

Keep the following in English:

- code;
- filenames;
- directory names;
- agent names;
- skill names;
- hook names;
- configuration keys;
- JSON property names;
- technical identifiers;
- slash-command names.

External research may use both Russian and English sources.

Do not unnecessarily translate product names, model numbers, manufacturer names, technical standards, URLs, or official terminology.

# Architecture Requirements

The eventual system must use a model-driven hub-and-spoke architecture.

The future architecture will contain:

```text
User
  |
  v
DIY Coordinator
  |
  +---- specialized subagents
  |
  +---- reusable skills
  |
  +---- MCP
  |
  +---- quality gates
  |
  +---- persisted workflow state
  |
  +---- human approval
  |
  v
Final Output
```

The coordinator will eventually be responsible for:

- understanding the request;
- gathering missing requirements;
- confirming requirements;
- creating an execution plan;
- dynamically selecting subagents;
- determining dependencies;
- running independent work in parallel;
- running dependent work sequentially;
- validating artifacts;
- handling targeted retries;
- persisting workflow state;
- resuming interrupted workflows;
- requesting explicit human approval;
- handling rejected results;
- triggering final output generation only after approval.

The coordinator must not become a general-purpose DIY researcher itself.

Specialized work should eventually belong to specialized subagents.

The future MVP should support at least these categories:

## 1. Product / Tool Decision

Example:

```text
/diy Стоит ли мне покупать этот фрезерный станок для мастерской?
```

## 2. Workshop Planning

Example:

```text
/diy Помоги спланировать первый этап обустройства моего гаража под столярную мастерскую.
```

## 3. DIY Project Planning

Example:

```text
/diy У меня уже куплена напольная плитка для мастерской. Помоги спланировать проект укладки пола.
```

These are examples of different workflow types.

The architecture must allow the coordinator to dynamically select only the agents required for the current task.

Do not design one fixed pipeline that runs every agent for every request.

# Future Agent Model

Do not implement these agents yet.

Instead, define their responsibilities and contracts in the architecture.

The initial conceptual agents are:

- `requirements-formalizer`
- `diy-researcher`
- `product-researcher`
- `project-planner`
- `cost-planner`
- `evidence-validator`
- `synthesizer`
- `final-output-builder`

For each agent, define:

- responsibility;
- inputs;
- outputs;
- owned artifacts;
- dependencies;
- what the agent must not do.

The architecture should make it possible to add new specialized agents later without changing the fundamental coordinator design.

# Artifact Model

Workflow artifacts should be human-readable Markdown files.

Do not use JSON as the primary format for agent-to-agent artifacts.

Use JSON primarily for machine-readable workflow state.

Agents should communicate primarily through persisted artifacts rather than copying large amounts of previous-agent output into prompts.

Each artifact must have one clear owner.

Future artifacts may include:

```text
requirements.md
research.md
products.md
project-plan.md
budget.md
validation.md
final-plan.md
```

Define the artifact lifecycle conceptually:

```text
created
    |
    v
validated
    |
    v
available to dependents
```

A failed artifact must not be treated as valid input for downstream work.

---

# Workflow State

The eventual workflow must persist execution state.

Conceptually:

```text
workflows/<run-id>/workflow-state.json
```

Define what information the state must contain.

At minimum consider:

- run ID;
- original request;
- workflow type;
- confirmed requirements;
- selected agents;
- execution plan;
- dependencies;
- completed work;
- failed work;
- retry counters;
- artifact paths;
- artifact validity;
- validation results;
- approval status;
- approval feedback;
- final output status.

The architecture must support resuming an interrupted workflow without unnecessarily repeating completed valid work.

---

# Quality Gates

Define the architecture for explicit quality gates.

At minimum, future validation should cover:

- confirmed requirements are addressed;
- important factual claims have sources;
- recommendations are traceable to requirements;
- current prices are sourced;
- budget constraints are respected;
- artifacts are structurally valid;
- artifacts do not contain unsupported invented facts;
- important uncertainties are explicit;
- downstream dependencies are satisfied.

Define how a failed gate should map back to the responsible artifact and agent.

The future system must support targeted retries rather than restarting the entire workflow.

Maximum retry count should be configurable, with an initial default of 3.

---

# Human Approval

The eventual workflow must require explicit human approval before final output generation.

Approval must be deterministic and represented in persisted workflow state.

The architecture should support states such as:

```text
awaiting_approval
approved
rejected
```

Approval must never be inferred from ambiguous conversation text.

A rejected result must be capable of entering a revision loop.

# MCP

MCP must eventually be used as a real architectural capability.

Do not select an MCP server merely because the assignment requires one.

First identify what external capability the DIY Assistant actually needs.

Then determine whether an existing community MCP server provides that capability.

Potential categories include:

- product/research information;
- YouTube or practical DIY content;
- access to the user's workshop/project knowledge;
- another external information source directly relevant to DIY tasks.

Do not choose the specific MCP server yet unless repository inspection reveals an obvious existing integration.

Instead:

1. identify likely MCP use cases;
2. identify candidate MCP capabilities;
3. explain which agent would use each capability;
4. explain what artifact would consume the result;
5. identify any credentials or configuration requirements;
6. recommend the most appropriate MCP approach for the next implementation step.

If no suitable community MCP exists, a small custom MCP server may be considered later.

- access tokens;
